The number is high but mostly driven by 2 corpus-quality issues (P3 scope mismatch, P4 PDF/pasiūlymas size mismatch). Per-line analysis below isolates the genuine AI accuracy issues.

## Top-3 systemic AI issues (Task 7.2 input)

### #1 — `plyteles_sienos_m2` consistently UNDER (€6.8k corpus impact)

| | P1 | P2 |
|---|----|----|
| GT (samatininkas) | 209.9 m² | 55.3 m² |
| AI prediction | 70.0 m² | 0.0 m² |
| Error | -67% | -100% |

**Root cause:** AI computes wall tiles as `perimetras × tile_height` only for `paskirtis ∈ {vonia, wc, san}`. Misses:
- Kitchen backsplash (no `paskirtis=virtuvė` rule)
- Hallway / accent wall tiles
- **Vonios išklotinės (wall elevation pages) NOT parsed** — `Vonios išklotinės pages: 0` for projektas_1 even though the PDF has them. Page classifier doesn't tag išklotinės reliably.

**Fix paths:** (a) add kitchen backsplash detection by `paskirtis=virtuvė` + standard 0.6m default, (b) wire wall-elevation page classifier into vision pipeline so užklotinės get parsed.

### #2 — `angokrasciai_gkp_m` consistently OVER (€4.4k corpus impact)

| | P1 | P2 |
|---|----|----|
| GT (samatininkas) | 94.0 m | 34.5 m |
| AI prediction | 202.5 m | 55.2 m |
| Error | +115% | +60% |

**Root cause:** AI counts angokraščiai = (2H + W) × 3-sided × **all openings** (windows + doors). LT samatininkai count only doors + paslėptos durys; for windows the bottom side is priced separately as palangė (window sill).

**Fix:** in the angokrasciai calc per room, subtract bottom side for windows when assumption `windows_have_palange=True` (default true). Recompute formula per window: 2H + W → 1H + W (top + 2 sides only, no bottom). This drops window contribution by ~30% and matches LT pricing convention.

### #3 — `lubos_virs_3m_m2` always 0 (€1.2k corpus impact)

| | P1 | P2-P4 |
|---|----|----|
| GT | 68.3 m² | 0 |
| AI prediction | **0** (all projects) | 0 |
| Error | -100% | — |

**Root cause:** AI defaults `lubu_aukstis_m=2.82` for every room — never auto-detects taller ceilings without a section view. The user has flagged this manually before (memory: "ceiling >3m not auto-detected on p1").

**Fix:** the user-override input already exists in Prielaidos panel. Need: (a) detect tall-ceiling room markers from floor plans (e.g. "+3000" annotations near room labels), (b) when detected, separate per-room `gkp_lubu_virs_3m_m2 = ceiling_area_for_h_above_3m` from standard `gkp_lubu_standart_m2`. Half of the fix exists in `extract_height_markers` from page-1 fallback (committed 2026-05-07); needs to also run on every floor-plan page, not just p1.

## Out-of-scope (not AI accuracy)

- **silikonas_m UNDER** — GT counts every fugavimo kampas that gets siliconed; AI emits silikonas only when paskirtis=vonia. Spec ambiguity.
- **P3 224% bundle over** — rangovas P3 pasiūlymas only bid lubos+sienos glaistymas (~250 m²), AI extracted full 814 m² interior. AI is correct, comparison is apples-to-oranges.
- **P4 89% under** — `projektas_4_breziniai.pdf` is 7-page subset (~20 m²) but the matching pasiūlymas covers a ~150 m² project. PDF/pasiūlymas pairing problem.

## What this benchmark IS for

- The **ranking** of EUR misses (#1 plyteles_sienos > #2 angokrasciai > #3 lubos virš 3m) is reliable — same top-3 emerged independently from random-mapped runs and real-extracted runs.
- **Corpus-level €25k aggregate** (sum of all abs deltas across 4 projects) shows the order-of-magnitude impact — fixing #1 alone saves ~€7k of estimation error per typical project pool.
