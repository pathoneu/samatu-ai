**Risks the worker named**

- Tab close while a PUT is in flight: the newest snapshot now waits for that PUT's answer. If the page is closed before the answer arrives, the waiting snapshot is not sent; it is still written to localStorage synchronously. Before, a replacement PUT was started on unload, but it was likely killed anyway (a >64 KB body cannot use keepalive). Tab switches (visibilitychange) are not affected because the page stays alive.
- If the network drops after the server has received a PUT (the answer is lost), the waiting snapshot goes out with the old base and can get a 409. This is the same false-conflict class as before, but now only on a real network failure, not on every fast save.
- The import compares the file's updated_at (client clock) with the server's updated_at (server clock), the same comparison refreshProjectFromBackend already uses. With a badly skewed client clock, an older file copy can look newer and overwrite the server's copy. The 409 guard only protects against changes made between the list read and the PUT.
- Projects whose import send failed are still only in the local cache, and the next Dashboard pull still replaces the whole cache. That is why the failure toast says to import the same file again. The pull itself was not changed.
- permanentlyDeleteProject now sends DELETE only after an in-flight PUT for that project is answered, instead of aborting the PUT. If that PUT hangs, the DELETE is delayed by the same time.
