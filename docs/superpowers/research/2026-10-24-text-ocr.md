## 1. Engines — what installs, and the comparison

**Install.** All three install on Apple Silicon. **PaddlePaddle has no wheel for Python 3.14** (`pip install paddlepaddle` in the backend venv: `ERROR: No matching distribution found for paddlepaddle`; the Dockerfile is `python:3.14-slim`), so PaddleOCR proper can only run in a 3.11–3.13 side process. **RapidOCR** runs the *same PaddleOCR models* (PP-OCRv6 medium detector + the PP-OCRv6 medium recogniser with Lithuanian `lt`) as ONNX on onnxruntime, which has 3.14 wheels; installed and tested in the 3.14 venv. Tesseract needs the system binary (Homebrew/apt) plus `lit.traineddata`.

**One trap found and fixed:** RapidOCR shrinks every image to 2000 px on its long side before detecting (`Global.max_side_len`), which turns a 300 DPI A3 sheet into ~100 DPI — the first 150 vs 300 DPI runs took the same time and read the same. `RapidEngine` sets `max_side_len` to 12000. PaddleOCR's detector has a hard 4000 px cap (`max_side_limit`, not exposed by the pipeline), so its „300 DPI" A3 is detected at ~242 DPI.

**Engine chosen: `rapid` (RapidOCR + PP-OCRv6 medium `lt`), 300 DPI, rotations (0°, 90°).** Why: it is the PaddleOCR the plan names (same detector and recogniser weights), it reads as well as PaddleOCR or better (dims 91,9 vs 88,5 %, j3 table 39/40), it is **3,7× faster** (24 s vs 88 s per A3 sheet), and it is the only one of the accurate two that runs on the backend's Python 3.14 (onnxruntime; no PaddlePaddle). Dependency footprint: `rapidocr` + `onnxruntime` (~20 MB wheels) + ~80 MB of model files (PP-OCRv6 det medium, rec medium, cls) that RapidOCR downloads on first use from modelscope — **for production the models should be vendored or baked into the image** (otherwise the first OCR call downloads from the internet; nothing is uploaded, but the plan's „local" should also mean „no runtime download"). The production dependency decision stays the manager's.

**150 vs 300 DPI.** Overall equal on dimension strings (91,2 vs 91,9 %), but 300 DPI is clearly better on the badge rule (32 vs 16 accepted — at 150 the boxes are looser and merge with neighbours) and on scanned diacritics (j3 12 vs 9); 150 is twice as fast and on j4 actually read *more* tiny 1–2-digit strings. Default 300 (`SAMATU_OCR_DPI` overrides).

**The 90° pass.** PP-OCR already turns vertical text crops itself, so on ordinary sheets the 90° pass adds a little (a: 252 → 271 dims) for 2,4× the time; on a drawing rotated on its page (j4) it matters: 0° only reads 86 words / 12 parsed strings, both passes 117 / 19. Kept.

**Confidence is not a safety net.** The engine's p50 confidence is 1,00 on every sheet (p10 0,88–1,00). The systematic error — short strings printed upside down read without the flip (j4: „80" → „08", „90" → „06", „190" → „060", „690" → „069"; j3: „900" → „006") — comes at confidence **0,94–1,00**. These are harmless today only because the dimension parser drops them (a dimension never starts with 0, two-digit strings are not parsed); any future consumer must apply the same rule, not a confidence threshold.

## 3. Lithuanian diacritics

Raw, the recogniser reads ė as é and ū as ü on small or rasterised type (a_flat: 141 of 251 diacritic words right; j3: 5 of 15). Those letters are not in the Lithuanian alphabet, so `lt_letters` maps é/è/ê → ė, É/È/Ê → Ė, ü/û → ū, Ü/Û → Ū (one-to-one only): a_flat **141 → 178 / 251 (56 → 71 %)**, j3 **5 → 12 / 15**. What remains wrong: Š read as S on 150-DPI raster („Saldytuvas"), į read as j („jvadas" — j is a Lithuanian letter, not foldable), Ų read as Ú („PATALPÚ" — Ų or Ū is ambiguous, left), and truncated words on the flattened raster („Mikr" for „Mikrobangė"). On clean renders (c, the synthetic test) names come out right.

**Source 3 did not fire on c or j4 — and on c that matters, because the written 1:50 is probably wrong.**
- **c:** source 3 needs wall faces from wall **fills**; c draws its walls as strokes (6 vertical / 10 horizontal faces on the whole sheet — 0 proposals), and c writes every dimension label horizontally, also for vertical spans. So source 4 answers: the OCR'd title-block „M 1:50", LOW, „nepatikrintas". **Check against the drawing:** three OCR'd strings that do sit on vector lines measure **1:59,4 („2000" → 95,5 pt), 1:59,3 („1650"), 1:58,7 („940")**, and the „3800" sofa line measured on the render gives ≈ 1:59,8. c is very likely printed reduced (≈ 84 %), the j2 pattern (writes 1:40, measures 1:45). At the written 1:50 every length on c would come out ~16 % short and areas ~30 % short. The LOW label and „patikrinkite mastelį" are the only protection — **c should not be outlined at the stated scale until a measurement confirms it** (the person's „Mastelis" line over an OCR'd string, or the hairline route below).
- **j4:** strings are in centimetres; `plan_dimensions._value_m` reads 3–5 digits as millimetres and drops anything under 0,30 m, so of ~79 correctly read numbers only the 19 ≥ 300 cm survive (no 2-digit ones at all), and source 3's cm factor finds no 5-string agreement. Experiment (not wired): the OCR strings put through `attach_dimension_lines` find their j4 hairlines and measure **1:9 as mm = ≈ 1:90 in cm**, which the line reader refuses (no plan scale; no written scale to confirm the units). The fix belongs in the strings' unit rule, not in OCR.

**What would make c and j4 measure (not done — each is a change outside this task's files):** (1) let the hairline matcher (source 2) take OCR strings — they are positioned well enough (centres within 3 pt on the synthetic test at 200 DPI); on c it needs c's dimension lines, which PDFium finds only partly (15 horizontal / 17 vertical); (2) a centimetre rule for strings: when a sheet's strings are mostly 2–3 digits and the cm reading lands on a standard scale, read them as cm (j4, j1); (3) the „Mastelis" gesture over an OCR'd string (`string_under_line` already takes any dims list — the route needs the OCR strings for a sheet without a text layer).

## 6. What wiring OCR into room_locator and the table reader would take (not done — another worker's files)

**Badges → `room_locator.locate_rooms`.** One import: replace `plan_area_annotations._iter_pages` with `text.layer.page_items` (flag-gated inside). Everything downstream already works on the items: `_badge_words(_words(chars))`, `to_display`, the title-block / zone filters. Measured: rapid at 300 DPI reads 38/42 of a's badges, 8/9 of j3's, 9/9 of j4's. Three things to settle: (a) OCR word boxes are padded (PP-OCR's unclip ratio): a's badges come out 9–14 pt tall vs ~7 pt in the text layer, j4's 14–15 pt; the absolute 6,5 / 14 pt caps reject some (32/38 accepted at 300 DPI, 16/36 at 150). togal-v2's new relative rule (a badge up to 2× the dimension-string height, merge f9d2ced6) suits OCR better, because both heights are inflated alike — re-measure with it. (b) The „touching number" and „table column" rules use pt gaps tuned on the text layer; OCR merges adjacent digits less predictably („600600" as one line split into two words on one pass). (c) Cost: 10–31 s per sheet at 300 DPI, so only sheets with no text layer should be OCR'd (what `layer.page_items` does) and the result cached with the project (today the cache is in-process only).

**Tables → the eksplikacija reader.** `pdfplumber_eksplikacija` reads pdfplumber `extract_words` + ruled `find_tables`. OCR words have the same keys after `page_items` → `_words` (text, x0, x1, top, bottom), so the column parser can take them; the ruling lines exist on j4 (vector) but not on a scan (j3) — there the reader's word-clustering fallback is the path. Measured cell reading: a p3 54/56, j3 39/40 (areas like „35.86", „96.53" exact; names after the fold). Two specific risks: decimal separators read as „," vs „." (seen once: „21,"), and Ų/Ū in names („PATALPÚ"). R3 holds by construction: every OCR value carries its source string (the word itself).

**Also needed for a scan like j3:** scale. A raster sheet has no vector faces or hairlines, so source 3 cannot work; only the written scale (LOW) or the person's line. The raster spike's wall mask could provide raster wall faces for source 3 — a separate task.

## 7. Tests

`backend/tests/test_text_ocr.py` — 18 tests:
