## §3 The three investigations

### 3a — click-model tool-card labels at 1280×720 (real regression, fixed in product)

Root cause: commit `f0790b4c` (2026-10-25) added the `scaleLine` tool to the `Skaityti brėžinį` group, pushing the tool-rail from 14 to 15 tiles. The labelled rail height became `15 × 32 + 21 + 20 + 8 = 529 px`, above the `chromeHeight < 545` threshold at 1280×720, triggering `railCompact = true` and hiding every label. The test's intent — labels visible at ≥ 1280 — was unchanged.

Fix: `frontend/src/components/viewer/ToolRail.jsx` — TILE_H 32 → 30, `gap-px` → `gap-0`. New labelled height `15 × 30 + 21 + 20 + 8 = 499 px`, threshold cleared at 1280×720. Labels visible at both viewports.

Verified: screenshot in test run `1280×720: rail 499 px of 534 px`. The test's intent (`labelled, inside the drawing, no page scroll`) passes.

### 3b — guidance „row deleted from ⋯ menu" (flaky, isolated via spec)

Root cause: `projectStore.js` debounces saves at 400 ms and sends `base_updated_at` as an optimistic-concurrency token. When the test's beforeEach `restoreStart()` races with the frontend's first write-through, the frontend's `base_updated_at` can be stale by the time the delete fires. The server returns 409 silently and the frontend keeps the optimistic 116 rows while the backend stays at 117. The test's `expect.poll` then times out expecting the server to drop to 116.

Fix (spec-side): read the baseline AFTER `page.waitForLoadState('networkidle')` so the initial write-through is drained first. The product's 409 "keep our copy" behaviour is correct for a real user with two tabs — the spec is the thing that needed to settle. Verified: isolated run passes `117 → 116 → 117` by the same timings.

### 3c — viewer-chrome B7 „a room focused from the list is framed" (flaky, isolated via spec)

Root cause: initial canvas tiles can still be laying out when the room click fires; the `zoomToArea` call runs over a mid-animation canvas and the ring lands far from centre. Alone, this normally finishes before the click.

Fix (spec-side): wait for `networkidle` after `openProject` so tile fetches drain before measuring. The product's framing math is correct once the tiles have landed. Verified: `focus 06: zoom 163 % → 458 %, centre off by 11 / 2 px` (well under the 20 % limit).

### 3d — viewer-chrome B6 „confirm box 300 px + deleted measurement comes back" (flaky, product-side quirk)

The brief did not call this out, but on this head it fails alone. Root cause: in `global-setup.js`, after choosing the start version the setup unconditionally calls `/api/projects/.../versions/.../restore`. If the project is ALREADY on that version (fresh pristine DB after globalTeardown), the restore handler still inserts a new `grazinta` version carrying the current content as "Prieš grąžinant" — and that new version has the SAME sha as both the original and the current project. `project_versions.list_versions` marks `dabartine = (sha == current_sha)`, so BOTH versions are tagged as current, and the drawer's `nth(1)` row has its Grąžinti button disabled (`row.current || busy`).

Fix (spec-side): skip the `/restore` call when the chosen version is already `dabartine = true`. One-liner in `global-setup.js`:

    const needsRestore = chosen.dabartine !== true;
    if (needsRestore) await api(...).

Verified: `confirm box 300 px; Esc closed the box, drawer stayed; measurement delete → Atšaukti → back`.

(A separate product-side cleanup — not inserting the no-op "Prieš grąžinant" when restoring to the already-current version — is a reasonable follow-up for the backend. Out of scope for this task.)
