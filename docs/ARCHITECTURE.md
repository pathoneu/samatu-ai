# Pathon — Architecture & Traps

The real data flow, a **"which file is canonical"** map so you don't edit a stale copy, and the known fragilities. Written 2026-07-06 (Fable 5 handoff); revised 2026-07-25 (viewer stack added; `interiorCalc.js` and the recompute callers corrected). Pairs with [`DEVELOPING.md`](DEVELOPING.md).

## Data flow (the happy path)

1. Contractor uploads a construction PDF → `POST /extract-interior` (`backend/main.py`).
2. **`extract_interior`** (`backend/extractor/vision_call.py`) — Claude Vision reads the pages → rooms (`patalpos`) + per-room elements. Multi-pass: native-PDF pass-1 with **voting**, a **zoom** pass, and **readers** (`apdailos_reader`, `doors_reader`, `sanitary_fixture_reader`, `eksplikacija_reader`, `page_classifier`).
3. **`calc_room_quantities`** (`backend/extractor/universal_rules.py`) — the **canonical deterministic LT formula engine**. Per-room → paintable area, tiles, GKP, reveals, corners, etc. Formulas are specified in `CLAUDE.md §1`.
4. **`_build_pozicijos_from_rooms`** (`vision_call.py`) — aggregates rooms → `pozicijos` (line items) and applies **consolidation** (paint into iki/virš-3m tiers; LED-niche glaistymas+dažymas into one line), gated by feature flags.
5. **`_emit_v8_compat_fields`** → `darbu_sarasas` — the flat list the UI table **and** the exporters read.
6. Frontend renders; the user types **prices (`kaina`)** onto `darbu_sarasas` lines.

## Recompute flow (Prielaidos / assumption edits)

There are **two live recompute endpoints** for different edit surfaces — don't assume either is dead:
- **`POST /api/recompute-quantities`** (`backend/api/recompute_quantities.py`) — the **AssumptionsPanel** path. `AssumptionsPanel` edit → `frontend/src/lib/recomputeApi.js` → `_apply_assumption_edits` mutates rooms (ceiling height, `walls_paint_override`) → `_build_pozicijos_from_rooms` rebuild → `darbu_sarasas`.
- **`POST /recompute-interior`** (`backend/main.py`) — the **room/polygon-edit** path, and today its **only** live caller: `handleRoomsChange` in `InteriorProject.jsx` (fires when the user edits a room primitive — plotas, perimetras, lubų aukštis, paskirtis — or on the `samatu:project-recompute` event dispatched by `projectStore.updateRoomPolygon`, i.e. viewer zone edits). Rebuilds `darbu_sarasas` + santrauka deterministically from the edited rooms; no Vision call. **Parity rule (2026-09-07):** it must give the SAME per-room numbers as a fresh extraction — it builds the calculator input through `api.recompute_quantities._calc_input` (openings derived from `elementai`, never the calculator's 1-door/1-window default) and runs `vision_call.derive_room_extras` afterwards (putty, paint, primer, hidroizoliacija, karnizas, LED, trace). Before that it counted phantom openings and kept the first run's material litres forever; `tests/test_recompute_interior_parity.py` pins both paths to the same fixture. **Corrections on both paths (2026-09-29):** a per-room height edit through Prielaidos runs the same per-room tail (`_apply_recalc`: every calculator key, then `derive_room_extras`), and his „Nedažomos” (`walls_paint_override`, sent in `rules_override` on every recompute) reaches the calculator as `walls_paint_factor_override: 0` on both paths — the one input every wall branch honours first. An opening he steps down to 0 counts 0 (`universal_rules.kiekis_units`), and the walls pass keeps the opening he emptied empty (`_angos_pasalintos` on the element, only in rooms marked `_angos_user_at`); `tests/test_user_overrides_win_2026_09_29.py`. **Conditional rows (2026-09-08):** a position the builder emits only under a condition („Pastolių nuoma" while a room is above 3 m) carries `_only_while` (not `_salyga` — see DEVELOPING.md, `_sa*` keys never leave FastAPI); both merges (`lib/mergeDarbuSarasas.js` pass 3 and `api/recompute_quantities` pass 3) DROP an unedited orphan that carries it instead of flagging it „pasenusi" — the P0 „never delete" rule still protects every unconditional row. The tile, floor and hidroizoliacija lines carry the same per-room ledger as the paint lines (so a bathroom's check sheet lists its tiles), and the ceiling materials follow the BILLED ceiling (`lubos_billed`, i.e. the anchor), not the per-room sum. Every other per-room line gets its ledger from `_attach_room_ledgers` (a label → per-room-value table at the end of the builder, 2026-09-10): the rooms must add up to the line (a cent of rounding lands on the largest room), a symbol count above the room count is stated as an `anchor` step, and a line the rooms do not explain stays unledgered rather than carrying a broken chain. (`RulesOverridePanel` also called this endpoint, but that component was **removed from the UI 2026-05-06** and its file was **deleted 2026-10-05** — don't cite it as the caller.)

Both run `calc_room_quantities` → `_build_pozicijos_from_rooms`. Frontend `onRecomputed` → **`mergeDarbuSarasasEdits`** re-attaches the user's prices to the rebuilt lines — **by `id` first (since 2026-09-02), then by label** (rename maps → id → label). Both callers send the same reader context through `frontend/src/lib/recomputeContext.js` (`_door_types`, symbol counts, tile specs, `_ceiling_anchor`, overrides) — a caller that forgets it gets a quieter sąmata for no visible reason.

## Position identity + contribution ledger (Patikra, 2026-09-02)

- **Every computed row carries a stable `id`** (`backend/extractor/position_id.py`: short hash of `normalize_skyrius(skyrius)` + the tier/Q/coat-stripped label, *tier-aware* on purpose — both iki/virš-3m lines are live at once). Hand-added rows get `rnk-…` (`frontend/src/lib/darbuRows.js`). Both merge layers (`api/recompute_quantities._merge_user_edits`, `lib/mergeDarbuSarasas.js`) match by id before label, carry `kaina_source`/`kaina_match_score`, put `Medžiagos` last, and re-establish id uniqueness on the merge output (`_reassign_duplicate_ids` / `reassignDuplicateIds` — canonical rows claim first, carried orphans take `-N` counting up). **The two layers must stay behaviourally identical** — every rule change lands on both with a test on both.
- **The builder EMITS provenance** for the wired families (paint sienų/lubų both tiers, kampai, grindjuostės): `contributions[] {room_nr, room_name, page, value, unit, terms{}, included_because, geometry}`, `excluded[] {room_nr, room_name, excluded_because}`, `roll_up[] {op ∈ sum|cap|share|coefficient|constant|anchor|round, label, value, note}` where every `roll_up[].value` is the running result and the LAST equals `kiekis`; `contributions_sum_to_total` says whether Σ contributions reproduces `kiekis` (false on the anchored ceiling and the capped grindjuostės). Contract + rationale: `backend/extractor/ledger.py` docstring. The ledger lives on `darbu_sarasas` only (stripped from `pozicijos` to halve blob growth). Never reverse-engineer contributions from labels downstream — that is how the retired `interior_v8/_build_trace_links` drifted.
- **Keystone guard:** `backend/tests/test_contribution_ledger.py::test_every_ledger_replays_to_its_kiekis` replays `roll_up` over `contributions` on every corpus fixture and must reproduce `kiekis` to ±0,01 (a `round` step is only allowed within max(0,05; 0,1 %)). User-facing ledger strings go through the same guide-don't-confess vocabulary guard as confidence reasons.
- **Renderers:** `RowDetailPanel` + `LedgerTree.jsx` (the evaluated tree; treats `roll_up` as authoritative whenever `contributions_sum_to_total` is false), `ReviewQueueSidebar` + `PatikraCard.jsx` (the guided loop: € risk queue via `lib/takeoffWorkflow.rankReviewRows`, „Jautriausia vieta", „Teisinga ✓"/„Pataisyti" → `AssumptionsPanel focusField`, ripple diff by id, „Įsiminta" counter from the `corrections` table, trust meter). Pure helpers live in `lib/ledger.js` / `lib/takeoffWorkflow.js` and never re-sum the ledger client-side.

## Room facts + evidence (the check sheet, 2026-09-04)

The founder direction after the council: *"perfect the CHECKING so it still saves time — not with AI dots, with normal explanations showing how, where, what."* Two read-only endpoints serve that screen. Neither computes a quantity; both only re-present what the pipeline already stored.

**`GET /api/projects/{id}/rooms/{room_nr}/facts`** (`backend/api/room_facts.py`, logic in `backend/extractor/room_facts.py`) — auth + owner-scoped exactly like `/api/projects/{id}`, `404` for an unknown project **or** room, and the response passes through `user_text.scrub_prose` on the way out (`sentence` and `formula` are in `PROSE_KEYS`).

```jsonc
{ "room": { "nr", "name", "page", "polygon_pct": [[x,y],…]|null,
            "marker_pct": [x,y]|null, "region_pct": [x0,y0,x1,y1]|null },
  "facts": [ { "key": "plotas|perimetras|aukstis|apdaila|angos|grindys",
               "value", "unit": "m²|m|vnt.|null",
               "status": "read|assumed|missing",
               "source": { "kind": "eksplikacija|planas|pjuvis|apdailos_lentele"
                                 + "|duru_zinynas|grindu_planas|prielaida|nera",
                           "page": int|null, "rect_pct": [x0,y0,x1,y1]|null },
               "sentence": "<plain LT, guide-don't-confess>",
               "crop_url": "/api/projects/{id}/evidence?page=…&rect=…&dpi=…"|null,
               "editable": { "field", "kind": "number|choice|count" },
               "details": [ … ]        // openings only: per-type count + mm sizes
             } ],
  "quantities": [ { "row_id", "aprasymas", "unit", "value",
                    "terms": {…}|null, "formula": "<LT, real numbers>"|null,
                    "geometry": "polygon|marker|none", "included_because" } ],
  "excluded":   [ { "row_id", "aprasymas", "reason" } ],
  "ledger_available": bool }
```

Four contract rules a renderer must not blur:
- **`source.kind` is where the VALUE came from; `source.page` + `rect_pct` are where to LOOK.** They differ on purpose for openings: sizes come from the durų žiniaraštis (`kind: "duru_zinynas"`) while the crop frames the room, because the *count* is what he checks.
- **A rectangle is only ever offered on the page it was measured on** (`room_facts.region_on_page`). Cross-page ⇒ `rect_pct: null` and the crop is the whole sheet — "read this drawing", not "look exactly here". The 2026-05 browser-side highlight is the post-mortem (`EksplikacijaSourcePopover.jsx`).
- **`status`** — `read` = a reader, a table or the user produced it; `assumed` = a default we chose (the sentence says what and why); `missing` = no value. `grindys` is `assumed` on every room without an explicit override, because **no lane reads a floor finish** — it is `ROOM_TYPE_RULES[paskirtis]["floor"]`.
- **`quantities` come from `darbu_sarasas[].contributions` only** — never `pozicijos` (the compat emit *moves* the ledger), never re-derived from labels. `terms` where the family emits them (kampai, grindjuostės); the paint family emits none, so its `formula` states the share honestly instead of inventing a decomposition. A `cap`/`anchor`/`share` roll-up step is appended to the sentence **in both branches** — a room's own addition can be perfectly explained and still not be what the line bills. `ledger_available: false` means the project was last recomputed before 2026-09-02: say "not computed yet", not "this room contributes nothing".

**`GET /api/projects/{id}/evidence?page=N&rect=x0,y0,x1,y1&dpi=110`** (`backend/api/evidence.py`) — a PNG of that page region (rect in page-percent, 0–1, padded to a legibility floor). `?room=<nr>` is shorthand for the room's polygon bbox, else its printed-number marker ± margin; a room with no geometry is a **404**, not a blank image. Owner-scoped, rate-limited on `_client_key` like the other heavy handlers, plain `def` (threadpool) because it is poppler + Pillow, dpi clamped to 40–160 **and** further reduced so no page exceeds 4000 px on its long edge. Cached on disk under `data_path("evidence_cache", …)` keyed by (project, page, rect, dpi), evicted oldest-first past 256 MB; ETag ⇒ 304. `404 "Brėžinys nerastas"` when the project predates durable PDF storage. The **returned crop is capped at 1600 px on its long edge** (`MAX_CROP_PX`), so a whole-sheet request is never legible at 1:1 — which is why the enlarged viewer (`EvidenceCrop.jsx` → `SheetViewer`, 2026-09-07) opens the WHOLE sheet fitted with the evidence rectangle outlined, and once a zoom settles asks the endpoint for the region that is on screen and lays that sharp crop over the fitted sheet. To place the overlay it replicates `_padded` in `frontend/src/lib/sheetZoom.js`; `backend/tests/test_evidence_padding_contract.py` and `sheetZoom.test.js` pin both sides to the same fixtures — change the padding rule in both places or the overlay drifts.

⚠️ **The eksplikacija row bbox is `[x0, top, x1, bottom]` in PDF points from the page TOP** (pdfplumber's frame), with `eksplikacija_page_{width,height}_pdf` alongside — pdf2image rasterises from the top too, so the conversion is a plain division and **a y-flip "fix" would mirror the row to the wrong end of the sheet**.

⚠️ **Never key an eksplikacija crop on the top-level `eksplikacija_source_page`.** That field is Vision's own guess; the deterministic reader that produced the bbox records its page separately. Measured on one corpus project they disagree (model 1, reader 2). Order: room `eksplikacija_source_page` → `_eksplikacija.eksplikacija_source_page` / the row's own `page` → top-level.

**Room areas without a table (2026-09-06).** When no eksplikacija merged, `extractor/plan_area_annotations.py` reads the designer's own room-area labels („37.86 m²" standing in the room, or beside the room name) from the PDF text layer (pypdfium2, one pass, every text direction in its own frame), pairs them with Vision's rooms by WHERE they stand (point-in-outline when the sheets share a frame; a label inside two outlines = the same room drawn twice → `_area_unconfirmed_reason = duplicate_of:NN`; a label inside none = a room the model never returned) and by value otherwise, flags a room no label supports (`_area_unconfirmed`, kept — never deleted) and anchors the ceilings to their sum. The same pass collects the designer's legend totals into `_autoriaus_kiekiai` (shown beside ours on the check sheet, never used). A room then carries `plotas_saltinis = "plano_uzrasas"` and `_plotas_uzrasas {page, value_m2, bbox, page_width, page_height}` — the bbox is in the same top-origin pdfplumber frame as the eksplikacija row, so the check sheet crops the label with the same plain division.

**Room perimeters from the plan's dimension strings (2026-09-10).** `extractor/plan_dimensions.py`, Step 2.44b, after the area lane. Every „3.400"/„530" string on the text pages, backed by the hairline under it from the vector layer (pypdfium2 page objects; the page's scale is the median value/length, shown as „M 1:50"); sheets of one storey that repeat the strings at the same spots are pooled. A room's pair is a width string whose LINE spans the room label's x and a height string whose line spans its y, the two lines closing a rectangle around the label, with plotis × ilgis = the label's area (+5 % over for an L-room's bounding box, at most 2 % under). Then `perimetras_m = 2 × (plotis + ilgis)`, `perimetras_saltinis = "plano_matmenys"`, the read figure kept as `_perimetras_pries_matmenis`, and `_perimetras_matmenys {page, plotis_m, ilgis_m, sandauga_m2, rect, mastelis, …}` for the check sheet's sentence and crop. Product exactness alone is NOT a signal (a pooled storey has ~250 strings; coincidences to the cent happen — objektas_g run 2) — an unbacked string never pairs, and a room no pair explains keeps Vision's figure; `sanity_checks.check_perimeter_geometric_minimum` names read perimeters under 4·√plotas. Zoom (Step 2.5) and `/recompute-interior` keep a lane perimeter; table (`eksplikacija`) and user perimeters are never touched.

**Apimtis — what he does and does not do (2026-09-06).** `project._apimtis` → `rules_override.apimtis` on every recompute → `extractor/scope.py`: excluded rooms are marked `_neskaiciuoti` (kept in `patalpos`, zeroed, skipped by the builder, the totals, the paint consolidation and the ceiling anchor); families off drop their rows + materials after the build; `lubos` ne_musu/itempiamos and `sienos_angos` neatimti map onto the existing per-room ceiling flags, the stretch set and a `deduct_openings` room rule. Stateless by design — nothing is persisted into the rooms. One room can also drop apdaila / grindys / plytelės (`patalpu_sritys_ne`, `FAMILY_ROOM_FIELDS`); Rotband is a choice (`rotband`, `rotband_dalis`) with a stated 30 % default, never a calibrated constant; the plan labels no room claimed (`_meta.plan_area_lane.unclaimed`, with positions) become rooms with one click on the general facts page (`lib/planLabels.js`).

## Sąmatos šablonas — the contractor's OWN layout (2026-09-04/05)

His five section headings are stable across all his sąmatas while his row
wording is not, so the artefact we derive from his sąmatas is a **family
skeleton in his sections and his labels** (`backend/extractor/samata_template.py`,
measured in `docs/superpowers/research/2026-09-04-template-holdout.md`: offers
73,2 % of his rows at zero precision cost). Contract:

- **Storage:** `samata_templates` table, owner-scoped like price lists
  (`api/samata_templates.py`: `GET/POST/DELETE /api/samata-templates`; `POST
  {samatas:[<parsed sąmata>…]}` derives one server-side, `{id, samatas}` merges
  — idempotent on the sąmata's source name).
- **Render:** `POST /api/projects/{id}/samata-render[?template_id&include_optional=0]`
  → `{eilutes, santrauka, sablonas}`. **Pure — writes nothing.** The body is
  optional: `{darbu_sarasas:[…], patalpos:[…]}` renders the rows the CLIENT is
  holding (the store is write-through and lags a keystroke; rendering the blob
  showed a typed number one edit late). Without a body the saved blob is used.
- **Row shape** = the export row shape (`skyrius`, `aprasymas`, `mato_vnt`,
  `kiekis`, `kaina`, `id`) plus flags: `_sablonas` (his row vs „Kita (iš
  brėžinio)"), `_sablono_eile` (family key), `_pildymas` ∈ `uzpildyta |
  pasiulymas | tuscia`, `_siulomas_kiekis` (greyed suggestion, never the value,
  never exported), `_saltinio_id` (the darbu_sarasas ids that fed the cell),
  `_pastaba`, `_daznumas` („įprasta"/„kartais"), `_patikslinimas`.
- **The three rules:** a cell fills only from a VERIFIED or LEDGERED row
  (`is_fillable`); nothing computed is lost (unconsumed rows land in „Kita (iš
  brėžinio)"); no new fuzzy matching (families come from the frozen concept
  table in `scripts/reconcile_samata_lines.py`, the one the scorecard is pinned
  to). A family he has billed on more than one line is *itemised*: one row per
  app row, his label plus our qualifier.
- **Declared family:** an app row carrying `_sablono_eile` is consumed by THAT
  family regardless of what the concept regex makes of its wording, and is
  never taken by a neighbour's concept. This is how a number typed into one of
  his blank cells comes back into his cell: the frontend writes a hand-added
  `rnk-` row with his label, his unit, `manual_override: true` and the family
  key (`frontend/src/lib/samataTemplate.typeQuantity`). „Teisinga ✓" on a
  suggested cell stamps `user_verified_at` on the source rows — the same stamp
  Patikra writes, so it counts for the scorecard and `build_ground_truth.py`.
- **Frontend:** the Sąmata step has a layout switch („Pathon" | „Kaip mano
  sąmatose", `ProjectMainView.jsx` → `SamataTemplateView.jsx`), shown only when
  the account has a template; the room sheet's last page lists his blank rows
  („Jūsų eilutės", `components/roomsheet/YourRowsPanel.jsx`); the export menu
  offers „Excel — kaip mano sąmatose" → `POST /generate-excel?layout=template`
  (his sections and order kept, a blank cell prints EMPTY — never „0,00 €" to
  his client). All three read `lib/samataTemplateApi.js`; the pure helpers and
  their tests are `lib/samataTemplate.js`.

## Export flow

`ExportModal` builds `{projektas, eilutes, prielaidos, patalpos}` (maps `darbu_sarasas → eilutes`) → `POST /export/excel` | `/export/pdf` → `generate_excel` / `generate_pdf` (`main.py`). Excel uses **live formulas** (`=SUBTOTAL`, `=ROUND(...*0.21)`) so the contractor can edit quantities/prices in Excel and totals recompute.

**Interior projects export through `ExportDropdown` → `ExportFilterModal`** (not `ExportModal`, which serves KŽ projects) → `POST /generate-excel` | `/generate-pdf`. Since 2026-10-16 (togal-v2 W8):

- **„Grupuoti pagal"** (Excel, Pathon layout): `grupavimas` in the `/generate-excel` body — `skyriai` (absent = today's layout, untouched), `patalpos`, `seimos`, `lapai`, `be_grupavimo`. The grouping is the pure `backend/api/export_grouping.group_export_lines` over the printed lines plus each line's room parts (`dalys` = the server's `contributions[]` × floor count, sent by `lib/exportGrouping.exportLinesWithParts`). Invariant (tests/test_export_grouping.py): every grouping keeps each line's quantity and the workbook total to the cent — shares that do not add up to the line get a labelled remainder row, and split lines' amounts are allocated by largest remainder and written as values (`_suma`). Grouped sheets add „Kaip gauta" (program + confidence, or his own number). The dialog's preview is the server's dry run `POST /api/projects/{id}/export-excel/preview`, the same function. `lapai` groups by the sheet a room is drawn on (`contributions[].page`), which on most projects is the one plan sheet.
- **„PDF su žymėjimais"** (`OverlayPdfDialog`): `POST /api/projects/{id}/export-overlay-pdf` (`backend/api/export_overlay_pdf.py`) renders the chosen sheets with PDFium and draws outlines (solid = his, dashed = proposed), measurements with metres at the viewer's effective scale (sent in `scales`), count marks and optionally the wall solid, with a legend per sheet; `dry_run` returns sheet 1 as a PNG. **Measurement points are divided by PDFium's page size** (`page.get_size()`), because that is what EmbedPDF's `page.size` is — on a /Rotate 90/270 page the *displayed* size, not the mediabox (measured with EmbedPDF's wasm, 2026-10-16). The `embedPdfAdapter` / `PageClicks` comments that call it the mediabox size are wrong for rotated pages.

## The viewer stack (three viewers exist — know which one you're in)

- **`TakeoffViewer`** (`frontend/src/components/viewer/TakeoffViewer.jsx`) — **the default.** Built on **EmbedPDF / PDFium** (`@embedpdf/*` 2.14.x). This is the commercial takeoff surface: room zones, measurement tools, click-to-fill.
- **`PageOverlayHost`** — mounted once per page by `TakeoffViewer`'s `renderPage`. It is the **single rotation wrapper**: base render + tiling + search layers **and** our overlays rotate together inside it. Never rotate one layer alone — that's how overlays slide off their rooms. Clicks arrive already un-rotated and un-zoomed, in **PDF-point space**; `makeEmbedAdapter` is the only coordinate boundary.
- **`RoomZoneLayer`** — the **red-ring** model (founder decision 2026-07-14): at rest the drawing is clean; selecting a room draws ONE red ring on that room's own printed number. Filled polygon zones still exist behind the toolbar Layers toggle (QA view). Synthesized/bbox geometry renders dashed + "apytikslė".
- **`MeasureLayer`** — distance / perimeter / area / count + calibration, in PDF-point space. Page scale auto-seeds from the extractor's own data (`autoPageScalesFromRooms` → median m² per point from `polygon_pct` + eksplikacija `plotas_m2`); the user can override via `CalibrateDialog`. Durable per-page scale rides the project blob (`lib/durableScale.js`), so it survives a cache clear.
- **Drawing geometry (2026-10-16).** `GET /api/projects/{id}/pages/{page}/geometry` (`backend/api/page_geometry.py`) returns the sheet's wall solid (`pdf_vectors.wall_fills` merged) as rings in display-frame page fractions, fetched once per (project, page) (`lib/pageGeometryApi.js`, `hooks/usePageGeometry.js`). `MeasureLayer` snaps to those corners and faces before the user's own measurements (`lib/drawingSnap.js`; orange square = wall corner, orange diamond = wall face, green circle = own measurement). `DrawingGeometryLayer` draws the solid with every room outline and `_angos_sienose` opening behind the wall-icon toggle (`samatu_viewer_walls` in localStorage). `OutlineEditLayer` edits the focused room's `polygon_pct` vertex by vertex („Redaguoti kontūrą"); „Išsaugoti" goes through `POST …/rooms/{nr}/outline-set` (`api/room_outline.py`), which measures the ring (`_konturas.saltinis = "nubrezta"`, `polygon_source = corrected`) and reruns `geometry_lane.apply_geometry` — the same read a click gets — then `InteriorWorkspace.handleRoomOutlineEdit` dispatches `samatu:project-recompute`. While editing, the top pill and status bar name every exit (drag · midpoint adds · double-click removes · Z undo · Enter save · Esc cancel), a live chip shows the ring's m² and m next to the table's area, a self-crossing ring turns red and cannot be saved, and every gesture is undoable. With a measure tool armed the status bar says whether the sheet has wall geometry to snap to; the walls layer carries its own legend. ## Known fragilities / gotchas

- **Price-label matching.** Prices carry across a recompute by lowercased `aprasymas`. If a line's label changes on rebuild (paint flips iki↔virš-3m when a ceiling height crosses 3.0 m), the price can silently drop. Patched with a **normalized-key pass-2** on both FE (`mergeDarbuSarasasEdits`) and BE (`_merge_user_edits`). The *correct permanent fix* is **stable line IDs** (hash of room + line-type + base description) — a queued task.
- **Stale-static demo.** The sample project's numbers are **hand-authored** (they don't derive from its rooms), so any recompute shifts them. That's why the sample is now **locked read-only** (`AssumptionsPanel` gates on `rawData.is_demo`). Real projects don't have this.
- **Project persistence.** The durable per-user store **shipped** — SQLite (`backend/db.py`), per-`user_id`, write-through: every mutation writes localStorage (instant) *and* `POST /api/projects` (durable, cross-device). Backend is the source of truth; localStorage is the offline cache, purged on logout. Residual edge: `pullProjectsFromBackend` **replaces the cache wholesale**, so a project that only ever existed in localStorage (created while the backend write was failing/offline) is dropped on the next pull. Rare, but real — it is not a merge.
- **Vite module cache.** In a long dev session, `seedDemoProject`'s dynamic `import('@/demoData')` can return a stale module — a fresh browser is fine.
- **No backend `--reload`** — see `DEVELOPING.md`.
- **Above-3m surface is a LOWER BOUND, structurally.** `calc_room_quantities` can place wall/ceiling area in the virš-3m tier only from a room's **nominal** `lubu_aukstis_m` (all-or-nothing at 3.0 m) or from the explicit `extra_walls_virs_3m_m2` / `high_ceiling_area_m2` primitives — and **no Vision lane produces those two**; they arrive only from a truth file or a human correction (see the `PRIMITIVE_KEYS` comment in `vision_call.py`). A coffer, soffit step or double-height slice inside a nominally ≤3 m room is therefore invisible, and so is the scaffolding it implies. Same for `extra_walls_m2`: `walls_gross = perim × H` cannot see a partition that is off the room outline. Both are now **disclosed** (project-level `lt_sanity` WARN + per-room `_virs_3m_source` / `_walls_lower_bound`), not silently absorbed. Measured case — Objektas A: contractor bills 150.59 m² "sienos aukštos" + 62.82 m² "lubos aukštos" while the only drawing-derived >3 m room (102, H=3.4) supplies 103.15 + 50.54. `truth.json` parks the 47.44 + 12.28 residual on room **110**, whose lubų planas and išklotinės both read **2800 mm** — so that fixture attribution is a *plug*, not measured room-110 geometry, and closing the gap by "fixing room 110" would be eval-fitting. See `ground_truth/objektas_a/vision_corrections.json` (which admits the tuning) and `backend/tests/test_virs_3m_lower_bound_disclosure.py`.
  - **Partly closed 2026-07-29** by the positioned-height-marker lane (below): Objektas A room 101 now reads its printed 3.4 m instead of Vision's 2.8 m, moving "GKP lubos virš 3m" from **−19.55% to −2.02%** without touching room 110's plug. The tier is still a lower bound in general — the lane raises a room's *nominal* height, it does not produce `high_ceiling_area_m2` — so a partial high zone inside a genuinely 2.8 m room remains invisible and disclosed.
- **Ceiling heights come from the altitude printed inside each room** (`extractor/height_markers.apply_positioned_marker_heights`, 2026-07-29). Two lanes: point-in-polygon when rooms carry outlines, else proximity to the room NUMBER printed on the same sheet. The fallback is the one that actually fires — on Objektas A exactly **1 of 11** rooms has any geometry, so the polygon lane's frame gate scores 1/1 and refuses; **the polygon lane has zero real-data coverage in the corpus** and is unproven outside unit tests. The lane may only **raise or confirm** a height, never lower one (a marker labels one ceiling *plane*; a lower marker in a double-height room would delete the tall zone). Its two thresholds — a distance cap and an ambiguity margin, both fractions of the page diagonal — are **calibrated on one project**: on Objektas A p6 honest markers sit ≤0.083 of the diagonal from their room number while the `+3100` legend key sits at 0.144, and the one marker that is nearer a *neighbour's* label than its own is dropped by the margin rather than misfiled. Runs identically in production and in `eval_harness._rerun_deterministic_tail`, so the harness measures what the app does.
- **The garažas GKP soffit ("karobkė") is not detectable and is not faked.** Objektas A's contractor bills 11.16 **linear m** of "GKP dėžučių montavimas ant lubų"; `truth.json` carries it as `gkp_extra_area_m2 = 10.05` **m²** on room 105 — a unit-converted back-derivation, not a measured area, and a GT-only override no extraction lane populates. The drawing gives no signal whatsoever: the garage ceiling reads `betonas` in both the AI extract and the truth file, and the strings *dėžut* / *karobk* / *žemin* appear on **none of the 17 pages**. The only rules that would close it ("a betonas-ceiling garažas gets a GKP soffit ≈ its ceiling area") would fire on every garage in every project on the evidence of one contractor's sąmata — the exact reference-vs-ground-truth confusion the corpus notes warn about. Consequence to expect: with room 101 fixed, **"GKP lubos iki 3m" reads −9.11%**, worse-looking than the previous +1.60% only because that figure was two errors cancelling. Closing it needs the contractor, not a heuristic.
- **No partial / fractional wall-count concept.** The engine paints a room's whole perimeter. There is no way to say "the contractor paints 4 of these 5 walls". The only automatic producer of `walls_paint_factor_override` is `tile_calculator.apply_tile_overrides_to_rooms`, and only when an išklotinė covers **≥90%** of the room's wall surface; `wall_adjacency.shared_with_neighbors_m` is **audit-only** and deliberately *not* subtracted from the paint perimeter. So Objektas A room 105 Garažas's `walls_paint_factor_override = 0.7988` (= contractor 31.45 / engine 39.375, derived in commit `d4e54f8`) is **unreachable from the drawings** — it encodes a contractor scope convention no drawing states. Expect a persistent ~+8 m² on that room from Vision inputs; the closure path is a human correction in the workspace, not a formula.

## Accuracy reality (measured 2026-10-05)

There is **no blind project**: every figure here was measured on drawings the engine was developed against, against ONE contractor's sąmatos, with each project's Vision read saved once (the eval re-runs today's deterministic engine on that read, so reading variance is not in these numbers, and every engine input is Vision-derived). From `eval_harness.py --totals-only --recompute` and `--rows --recompute`:
- His **billed lines** (paint, kampai, angokraščiai, GKP lubos, Rotband, plytelės; Σ of his rows vs Σ of ours per family): **22,6 %** mean error over six projects — 6,2 % on objektas_a, 56,8 % on objektas_g.
- His **rows** reproduced within ±10 %: **28,2 %**.
- The formulas are not "solved": fed objektas_a's hand-entered room dimensions (`--use-gt-inputs`, the only project that has them, some back-derived from his sąmata — see the room 110 and garage notes above), walls still read −7,4 % and combined paint −5,4 %. objektas_g's corners read +136 % under today's corner convention, which is an open founder question, not a detection error.
- The old headline (walls / ceilings / LED / floor, „9,47 % in-sample, 7,06 % out-of-sample") scored copies — ceilings and the floor total equal the room table's printed total on both sides — and its out-of-sample projects had been tuned on. It is still printed as the legacy figure.

So: measure the billed lines and the rows before and after any change to a billed quantity (`DEVELOPING.md` › Measure accuracy), never tune to a sąmata, and get a blind batch, ideally from a second contractor ([`superpowers/plans/2026-10-05-blind-batch-protocol.md`](superpowers/plans/2026-10-05-blind-batch-protocol.md)), before quoting any number as how the product does on a new drawing. Symbol counting (difūzoriai, electrical, windows) has a real detection ceiling — an industry-wide ~0,40–0,55 exact-match per `docs/superpowers/research/2026-09-04-deep-research-claims.md`, a research claim not measured here — which is why fast correction UX is the leverage for counts.

## Security invariants (keep these true)

- Every project-scoped endpoint **requires auth** and **scopes the DB query by `user_id`** (read + write). `db.upsert_project` has an ownership barrier that blocks overwriting another user's — or a NULL-owner orphan — project.
- Vision runs **only after** auth (no unauthenticated budget-drain). Uploads capped at 200 MB.
- Excel/PDF export: sanitize **any user text written to a cell** with `_safe_cell()` (spreadsheet formula-injection). New cells that render `projektas` / room names / notes must use it.
- No `dangerouslySetInnerHTML` on user data (the only sink is an app-controlled chart-CSS helper). React auto-escapes everything else.
